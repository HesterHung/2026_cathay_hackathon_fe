# Cathay Cargo Offload Demo — Project Review

## 1. Executive assessment

The project is a navigable frontend demonstration of cargo offload risk, prevention review, and recovery comparison. Its strongest operational choice is to keep **forecast risk** separate from **confirmed offload/recovery** records. It also presents human review as a step before a decision and avoids claiming solver optimality in the recovery workflow.

It is not an AI prediction system or an airline operations integration. The displayed flight forecasts, outcomes, costs, weather evidence, and lifecycle states are hard-coded synthetic fixtures. The dashboard's calculation layer uses deterministic rules; there is no trained model, backend, API, authentication, or live operational feed. The separate generated cargo dataset in `data/` is not loaded by the UI. This is acceptable for a frontend hackathon demo when the presentation states those boundaries clearly.

The project is suitable for demonstrating a **workflow concept**, but not for claiming prediction accuracy, preventable savings, operational feasibility, or production readiness. Remaining judge risk centers on the meaning of the risk percentages, the synthetic and disconnected data, and the unsupported assumptions inside recovery cost and feasibility calculations.

## 2. Project architecture

- `fe/cargo-dashboard/src/main.tsx` mounts the React application. Vite, TypeScript, and React are the frontend stack; there is no backend project in the repository.
- `src/App.tsx` owns navigation state, shared drawers, shipment/customer detail views, and the Predictions and Analytics views. The Overview, Prevention Plan, and Recovery Plans pages are separate components.
- `src/domain.ts` contains both small dashboard fixtures and the deterministic forecast, scenario, value, lifecycle, and analytics calculations. It is the dashboard's current source of data.
- `src/OverviewControlTower.tsx`, `PreventionPlanPage.tsx`, and `RecoveryComparisonPage.tsx` implement the main operational screens. `OffloadTrendChart.tsx` renders a custom SVG trend chart; there is no charting dependency.
- Review decisions are written to browser `localStorage`. Navigation and filters are local component state; there is no server-side persistence.
- `data/synthetic_cargo` and `data/synthetic_cargo_csv` are separate generated datasets with Python generation and validation scripts. The UI does not import these records. Dashboard IDs such as `CX-482901` and recovery case IDs such as `RC-257-LHR` belong to its in-code fixtures, not the Python dataset's `SHP-` / `TM-` identifiers. The dataset README explicitly says its schema is not officially ONE Record compliant.
- The UI includes responsive breakpoints, filter/sort controls, empty states, risk queues, shipment links, and explicit simulated-data labels. `domain.test.ts` covers important calculations and risk/recovery separation.

The dependency and runtime footprint is small, and the UI contains no API credentials or real customer data. There is no auth boundary because there is no service. Decision storage is browser-local; storage parse/write failures are now caught by the review drawer and displayed to the user, but there is no server-side persistence. `App.tsx` also retains duplicate/legacy page implementations beside the active components, which can let labels or logic drift. Static pages need no loading state, but a connected version would need source freshness, fetch errors, and permission handling.

### Current flow

Static TypeScript fixtures → deterministic domain formulas → overview and prediction tables → selection opens a detail/review drawer → prevention or recovery comparisons → optional local browser review record. There is no operational outcome ingestion loop; Analytics reads another fixed four-flight fixture rather than results generated by user actions.

## 5. Prediction and recovery assessment

### Before an offload

- The intended target appears to be cargo shipment offload due to flight capacity/weather/fuel conditions. The event definition, eligible denominator, and prediction horizon must be agreed before real model work.
- The demo forecast uses synthetic booked weight, payload, fuel delta, weather severity, and route conditions. The formula estimates `shortfall / booked weight` and derives a separate capped risk score from that share and fixed weather floors. It is deterministic, not learned from outcomes.
- The static `forecastConfidence` values are fixture inputs, not statistical model confidence. The UI now identifies weather-input confidence where shown.
- There is no feature store, training pipeline, temporal validation, calibration curve, or leakage analysis to audit. The demo trend fixtures do preserve fixed 24-hour forecast snapshots, which is a useful shape for a future leakage-safe evaluation, but they are not operational history.
- The dashboard distinguishes flight risk from affected shipment records in several places. Always keep the unit and denominator beside a percentage. Do not treat a capacity-weight shortfall as a shipment-level offload rate.

### After an offload

- Lifecycle fixture records separate forecast risk from confirmed operational events/authorized decisions, and route the two categories to Prevention and Recovery respectively. This is a good workflow distinction.
- Recovery candidates expose capacity, arrival, delay, cost, and network-effect fields. The evaluator is a heuristic and cannot establish real feasibility or global optimality; some constraints are unavailable and the modeled network impact is approximate.
- The review drawer requires a reason and writes a simulated decision to local storage. It does not book, assign, or re-route cargo.
- Recovery outcome measurement is not connected to those decisions. The fixed Analytics outcomes cannot demonstrate that an action caused an improvement.

## 6. UI/UX assessment and workflow

The existing visual system already has a restrained forest-green, white, charcoal, and grey palette, dense tables, responsive layouts, a route map, and a custom trend visualization. The strongest screen model is:

1. **Overview:** “What needs attention?” Separate prevention and confirmed recovery queues; open the corresponding workflow.
2. **Predictions:** “Why is this flight flagged?” Search/filter/sort the synthetic flights and inspect fuel/weather/capacity evidence. The recalculation control has been removed because the fixture is static.
3. **Prevention Plan:** “What options could reduce the modeled risk?” Compare simulated candidates and inspect trade-offs; do not suggest an action was executed.
4. **Recovery Plans:** “What can be done after a confirmed event?” Compare alternatives for the selected recovery case and record a review decision locally.
5. **Shipments:** “Which customer cargo is exposed?” Compare illustrative cargo and carrier impact estimates with their assumptions.
6. **Analytics:** “What does this tiny sample show?” Separate binary flight flags, per-flight rate error, aggregate rate gap, and outcome counts; prominently retain the insufficient-sample notice.

The requested page-heading eyebrows were removed, and the top padding was reduced on headings that begin directly with the page title. Remaining UI improvements should focus on keyboard-operable table rows, explicit empty states for unavailable chart metrics, and consistently named source confidence. Avoid adding fake live controls.

## 7. KPI and claim definitions

- **Offload event / rate:** define cargo vs flight counting, eligible population, and reporting window. Demo actual rate `42 / 1,000 = 4.2%` is a fixed synthetic fixture.
- **Predicted rate:** the percentage of classified flight records flagged by the demo rule is not the same as the capacity-weight shortfall share. The Analytics labels now say “Flights flagged by prediction” and “Flights with recorded offload.”
- **Forecast shortfall:** percentage is `capacity shortfall / booked cargo weight`, not an offload probability or a percentage of shipments.
- **Risk score:** a deterministic heuristic percentage; not calibrated probability.
- **False alarm / missed offload:** computed over binary flight flags in the four-record synthetic outcome set. Denominators are shown by the Analytics metric labels.
- **Mean absolute per-flight rate error:** the mean absolute difference between the fixture's per-flight predicted and actual rates; the current sample gives **5.5 percentage points**.
- **Aggregate flight-rate gap:** absolute difference between the mean predicted and actual per-flight rates; this is now calculated separately and gives **3.0 percentage points** on the current fixtures.
- **Intervention success:** records with intervention and no actual offload divided by intervention records. The UI correctly states this association is not causation; the sample is only 2/2.
- **Value at risk / modeled loss / potential loss avoidable:** scenario proxies derived from synthetic constants. They are not cargo claims, realized loss, or verified Cathay savings.
- **Confidence:** source/weather fixture confidence, not calibrated confidence in an ML forecast.

## 8. Implementation roadmap

### Critical

- Agree and document the exact cargo offload target, event timestamp, eligible denominator, and action horizon.
- Keep risk-score labels, units, denominator, synthetic source, and timestamp visible in every relevant view.
- Keep demo and future operational data boundaries explicit; do not describe this build as an AI model or live system.

### High

- Create an explicit adapter from the generated dataset to UI view models; validate IDs, timestamps, and units at the boundary.
- Replace string-based deadline checks and arbitrary feasibility gates with explicit, typed constraints; unknown inputs must not be called feasible.
- Build time-ordered forecast/outcome fixtures and report calibration, precision/recall, false alarms, misses, warning lead time, and sample sizes separately.
- Add keyboard interaction and focus semantics to clickable rows; show clear no-data states for unavailable chart series.

### Medium

- Make scenario timestamps a single configuration value and display the same fixed demo snapshot consistently.
- Add a visible local-only decision receipt and a way to clear demo decisions; guard localStorage parsing and writes.
- Consolidate duplicate legacy page implementations in `App.tsx` after confirming no navigation path depends on them.

### Low

- Continue consolidating repeated CSS breakpoints/design tokens and document the nonstandard synthetic ID prefixes.
- If real data is later connected, add stale-source indicators, loading/error states, and access controls at the service boundary.

## 9. Changes made and validation

- Removed the requested page eyebrow labels and reduced extra top padding where the title now starts the heading.
- Removed the inert “Recalculate forecast” button from the static prediction page.
- Renamed the capacity metric to forecast booked-weight shortfall, described its denominator, changed the table to “Forecast shortfall,” and marked the output as an illustrative rule-based score with no trained model or live feed.
- Replaced relative “Today/Tomorrow” forecast labels with fixed UTC demo dates.
- Renamed Analytics binary flight metrics to describe flight records and computed the aggregate predicted/actual rate gap separately from mean absolute per-flight error. Added a regression assertion for the 5.5 pp and 3.0 pp values.
- Replaced the generated Vite starter README with frontend-demo scope, workflow, data-boundary, and limitation notes.

Validation run from `fe/cargo-dashboard`:

- `npm test` — 30 tests passed.
- `npm run lint` — passed.
- `npm run build` — passed.

The Python dataset validator also passed with 0 errors and 0 warnings. No browser-based accessibility audit or live airline integration was possible or in scope for this frontend-only build.

## 10. Judge-readiness assessment

**Ready to present as a frontend workflow prototype with synthetic data. Not ready to present as an AI predictor, validated optimizer, measurable savings product, or operationally integrated system.** Lead with the problem workflow and the separation between predicted and confirmed events. Show one case end to end, explain the illustrative formulas, and state plainly that the generated dataset is not connected to the dashboard. The next evidence that would materially improve the claim is a validated event definition, representative timestamped history, a leakage-safe baseline comparison, and confirmed recovery constraints/outcomes.
